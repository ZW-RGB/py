## 1. 项目概述

### 1.1 项目背景

智慧康养平台是基于 **若依 (RuoYi-Vue)** 框架构建的后台管理系统，部署在内网环境 (`http://192.168.18.143:1024`)。该平台管理着长者护理、入住处理、健康监测、合同管理、社区信息等 **21 张数据表**，涵盖老年人服务的全生命周期。传统爬虫依赖 XPath/CSS 选择器定位网页元素，面对 SPA（单页应用）页面改动时需要频繁维护，不具备自适应能力。

### 1.2 项目目标

构建一套 **LLM 驱动的自适应智能采集系统**，实现：

| 目标 | 说明 |
|------|------|
| **零选择器依赖** | 不编写任何 XPath/CSS 选择器，LLM 自动理解页面结构 |
| **自适应适配** | 页面改版或字段变更时，LLM 重新推理，无需改代码 |
| **API 直调模式** | 识别 SPA 架构后，转 API 直接调用后端接口获取 JSON 数据 |
| **自然语言交互** | 用户用中文描述需求（如"导出所有长者的姓名和联系方式"），LLM 解析为爬取规则 |
| **反馈自学习** | 记录用户对解析结果的确认/修正，历史相似查询自动 boost 正确端点 |
| **配置外置化** | API 端点与前端路由从代码中抽离到 YAML 文件，支持热重载，平台结构变化无需改代码 |
| **路由自动发现** | Playwright 自动扫描侧边栏菜单，发现新增路由并合并到配置 |
| **多格式导出** | 支持 CSV / JSON / Excel / TXT 四种导出格式 |
| **Web 可视化管理** | Flask 控制台提供标准模式 + 智能模式 + 页面采集三模采集 |

## 2. 核心设计思路

### 2.1 设计哲学

```
传统爬虫：人工分析 DOM → 编写选择器 → 数据提取 → 格式转换
本系统：  自然语言意图 → LLM 解析目标 → API/HTML 自适应获取 → LLM 字段映射 → 结构化输出
```

**核心原则**：让 LLM 成为爬虫的"大脑"，而不是让爬虫去适配每一个页面。

### 2.2 三模采集架构

#### 第一阶段：API 端点发现

针对 Vue.js SPA（若依框架）的特点，直接分析平台的 JavaScript bundle（`chunk-vendors.js` + `app.js`），从中提取后端 API 端点路径。

- 下载 JS 文件 → 正则匹配路由定义 → 提取 `/dev-api/**/list` 路径 → 构建端点清单
- 结果：发现并验证了 21 个可用数据 API 端点，外置到 `kangyang/config/endpoints.yaml`

#### 第二阶段：三模数据采集

| 模式 | 路径 | 适用场景 |
|------|------|----------|
| **标准模式** | 用户勾选数据表 → 批量 API 分页拉取 → 预设字段输出 | 常规批量数据采集、定时同步 |
| **智能模式** | 自然语言输入 → LLM 意图解析 → 动态字段映射 → 按需输出 | 临时查询、"想爬什么就说什么" |
| **页面模式** | Playwright 无头浏览器 → 自动登录 → 页面全量采集 → 表格/表单/文本提取 | 需要完整页面内容（含文本、图片、链接）、分页数据采集 |

### 2.3 LLM 的多重角色

| 角色 | 用在何处 | 具体能力 |
|------|----------|----------|
| **意图解析器** | `intent_parser.py` | 将"帮我导出所有护士的姓名、工号和科室"解析为 `{target_api, fields, confidence}`（v5：8 层加权评分引擎 + 同义词组 + 否定排除） |
| **字段映射器** | `intent_parser.py` | 原始 JSON key 是 `nurseName`/`deptId`，LLM 将其映射到用户要求的"姓名"/"科室" |
| **语义提取器** | `llm/parser.py` | HTML 模式下，从网页纯文本中理解并提取 title/publish_date/summary 等结构化信息 |
| **反馈学习者** | `query_feedback.py` | 记录用户确认/修正行为，相似查询再次出现时自动 boost 历史正确端点 |

```
│                       数据获取层                              │
│  Scrapy 2.x (HTML 模式) + 标准库 urllib (API 模式)           │
```

### 3.2 技术选型理由

| 技术 | 版本 | 选型理由 |
|------|------|----------|
| **Python** | 3.8+ | 爬虫/数据处理生态最完善，LLM SDK 原生支持 |
| **Flask** | 3.x | 轻量级 Web 框架，适合控制台类应用，无 ORM 束缚 |
| **Scrapy** | 2.x | 企业级爬虫框架，中间件/Pipeline 架构利于扩展 |
| **LangChain** | latest | OpenAI 兼容接口抽象层，统一多种 LLM 调用方式 |
| **deepseek-v4-pro** | — | 中文理解能力强，MaaS 私有部署保证数据安全 |
| **SQLAlchemy** | 2.x | Python 最成熟的 ORM，QueuePool 连接池管理 |
| **openpyxl** | latest | 纯 Python Excel 写入，无需依赖 MS Office |
| **Vanilla JS** | ES6+ | 前端无框架依赖，Jinja2 模板注入数据，部署零构建 |

### 3.3 Playwright 的角色定位

项目的核心采集策略是 **API 直调**，但在 v2.0 之后引入了 Playwright 作为**补充采集模式**：

| 对比维度 | API 直调 (主力) | Playwright 页面采集 (补充) |
|----------|---------------------|---------------------|
| 速度 | 快（直接 HTTP 请求） | 较慢（页面渲染 + 等待） |
| 稳定性 | 后端 API 相对稳定 | 受页面改版影响 |
| 资源消耗 | 低（纯 HTTP 请求） | 高（浏览器进程） |
| 数据范围 | API 暴露的结构化数据 | 完整页面内容（文本/表格/图片/链接） |
| 适用场景 | 批量数据拉取、定时同步 | 需要完整页面内容、分页数据采集、路由自动发现 |

Playwright 主要用于两类场景：
1. **页面全量采集**：提取 API 不暴露的页面级内容（富文本、图片、链接关系）
2. **侧边栏路由自动发现**：登录后扫描若依菜单结构，自动发现新增路由

## 4. 技术路线

### 4.1 项目演进路线

```
Phase 1 ───→ Phase 2 ───→ Phase 3 ───→ Phase 4 ───→ Phase 5 ───→ Phase 6
爬虫原型    API 模式     Web 控制台   自然语言交互   v5 精准度    配置外置化
(Scrapy)    (RuoYi API)  (Flask)      (Intent Parser) 优化         + 路由发现
```

### 4.2 Phase 1：爬虫原型（Scrapy + LLM）

**目标**：验证 LLM 从网页 HTML 中提取结构化数据的可行性。

**实现**：
- 基于 Scrapy 框架构建爬虫骨架
- 设计 `RawPageItem → ParsedItem` 两级 Item 流
- 引入 LangChain ChatOpenAI 作为 LLM 调用层
- Prompt 构建器注入 Schema 定义 + Few-shot 示例
- MockLLM 作为离线开发兜底

**产出**：
- `kangyang/spiders/kangyang_spider.py` — 零 XPath 爬虫
- `kangyang/llm/parser.py` — LLM 解析引擎
- `kangyang/llm/prompt.py` — Prompt 模板系统

### 4.3 Phase 2：API 直调模式

**原因**：发现目标平台是 Vue.js SPA（若依框架），前端 HTML 不含数据，数据完全通过 AJAX 请求后端 API 获取。

**实现**：
- 分析 JS bundle 提取 API 端点（`find_api.py` / `find_api2.py`）
- 构建 `RuoYiApiClient` 处理登录、Token 续期、分页拉取
- 建立 `KNOWN_ENDPOINTS` 字典（21 个数据表 → API 路径映射）
- `api_crawler.py` 遍历所有端点，批量拉取数据

**技术要点**：
```
登录: POST /dev-api/login → {"token":"xxx"} → Authorization: Bearer {token}
分页: GET /dev-api/{module}/{table}/list?pageNum=1&pageSize=100 → {"rows":[...],"total":N}
Token续期: 401 → 清除token → 重新登录 → 重试
```

### 4.4 Phase 3：Web 可视化控制台

**目标**：从命令行工具升级为 Web 界面，降低使用门槛。

**实现**：
- Flask 后端：12 个 RESTful API，双线程状态管理
- 前端：Vanilla JS 单页应用，深色主题，双标签页
- 标准模式：表列表勾选 → 批量爬取 → 实时进度 → 结果预览
- 导出引擎：CSV（UTF-8 BOM）/ JSON / Excel（多 Sheet 样式）/ TXT

### 4.5 Phase 4：自然语言智能交互

**目标**：用户不需要知道 API 路径、字段名等技术细节，只需用中文描述需求。

**实现**：
- `intent_parser.py`：LLM 将自然语言解析为 `{target_api, fields, confidence}` 三元组
- 两轮 LLM 调用：意图解析 → 字段映射
- 前端：交互式确认流程（解析预览 → 确认 → 执行 → 展示）

**设计原则**：
```
用户视角："帮我导出所有护士的姓名和工号"
        ↓ LLM 意图解析
系统视角：POST /dev-api/basicinformation/nurse/list
        提取字段: nurseName, jobNumber
        ↓ LLM 字段映射
输出表格：姓名 | 工号
```

### 4.6 Phase 5：智能模式 v5 精准度优化

**目标**：针对用户反馈的智能模式精准度不足问题，从 4 个维度全面提升自然语言解析准确性。

**维度 1 — 多维加权评分引擎**：替代 v3 的扁平打分，引入 8 层评分体系：

| 层级 | 评分 | 匹配方式 |
|------|------|----------|
| L1 | 1.0 | 精确名称匹配 |
| L2 | 0.9 | 语义映射表匹配（口语→标准词） |
| L3 | 0.8 | 别名精确匹配 |
| L4 | 0.7 | 缩写展开匹配（"体检"→"能力评估"） |
| L5 | 0.6 | 同义词组匹配（"老人家"→"老人"） |
| L6 | 0.4 | 部分关键词匹配 |
| L7 | 0.3 | 模糊匹配（阈值 0.70） |
| L8 | 0.1~0.15 | 模块/路径兜底匹配 |

**维度 2 — 同义词与缩写映射扩展**：
- `SYNONYM_GROUPS`：25 组近义词聚类（"看护"→"护理"、"脉搏"→"心率"）
- `ABBREVIATION_MAP`：17 条缩写展开（"护工"→"护士信息"、"退住"→"入住概览"）
- 字段同义词 97 条，自动标准化（"联系电话"→"联系方式"）

**维度 3 — 查询过滤条件优化**：
- **否定排除** `_extract_negated_terms()`：识别"不要""排除""除了"等否定词，排除对应端点和字段
- **字段-端点消歧**：字段级提示选择最佳端点（"老人的心率"优先匹配心率监测而非老人护理）
- **LLM 后验过滤**：LLM 返回被否定端点时自动回退到规则结果

**维度 4 — 用户反馈自学习**：
- 新建 `query_feedback.py`，自动记录每次查询的解析结果
- `get_feedback_boost()`：相似查询再次出现时自动 boost 历史确认的端点
- 文件存储到 `output/feedback/feedback_history.json`，5 秒内存缓存

**测试结果**：50 用例全部通过，v3 回归 10/10 无回归。

### 4.7 Phase 6：配置外置化 + 路由自动发现

**目标**：消除代码中的硬编码配置，使平台结构变化时无需修改 Python 代码。

**改造 1 — YAML 配置外置**：

```
kangyang/config/
├── endpoints.yaml      # 21 个 API 端点（模块/名称/路径/描述）
├── routes.yaml         # 22 个 Vue 前端路由（路径/名称/模块）
├── config_loader.py    # 统一加载器（线程安全、缓存、热重载、回退默认值）
└── __init__.py         # 对外 API：get_endpoints()/get_routes()/reload_config()
```

- `api_crawler.py`：`KNOWN_ENDPOINTS` 改为从 `get_endpoints()` 动态加载
- `page_scraper.py`：`KNOWN_ROUTES` 改为从 `get_routes()` 动态加载
- YAML 损坏/缺失时自动回退到代码内置默认值，保证服务不中断

**改造 2 — 侧边栏路由自动发现**：

- 新建 `route_discovery.py`，登录后用 Playwright 扫描若依侧边栏菜单
- 3 级回退策略：
  1. 提取 `.el-menu-item` 的 `index` 属性（Vue Router 模式，最可靠）
  2. 提取 `<a>` 标签的 `href` 属性
  3. 逐个点击菜单项，观察 URL 变化
- `discover_and_merge()` 一键发现 + 合并到全局配置（支持 append/replace 策略）

### 4.8 技术路线关键决策

| 决策节点 | 方案 A | 方案 B | 最终选择 | 原因 |
|----------|--------|--------|----------|------|
| 页面渲染 | Selenium 浏览器模拟 | API 直调 | **API 直调为主，Playwright 为辅** | SPA 数据经 API 暴露，跳过渲染层为默认策略；Playwright 用于页面全量采集和路由发现 |
| LLM 调用 | DashScope 公共 API | MaaS 私有部署 | **MaaS 私有部署** | 数据不出内网，安全性更高 |
| LLM 模型 | qwen2.5-7b | deepseek-v4-pro | **deepseek-v4-pro** | 中文理解更准确，JSON 格式输出更稳定 |
| 数据存储 | 纯文件 (JSON) | MySQL + 文件双写 | **双写** | MySQL 用于长期管理，文件用于快速查看/导出 |
| Web 框架 | Django | Flask | **Flask** | 轻量级控制台不需要 Django 的全套 ORM/Admin |
| 配置管理 | 代码硬编码 | YAML 外置化 | **YAML + 自动发现** | 平台结构变化时只改 YAML 不改代码，路由发现自动补充 |
| 意图解析 | 单一 LLM 调用 | 规则评分 + LLM + 反馈 | **三层融合** | 规则引擎保证稳定（8 层评分），LLM 处理语义歧义，反馈持续优化 |

```python
def _rule_based_match_endpoint(user_query, history_context):

    # 查历史反馈，boost 之前确认过的端点
    feedback_boost = get_feedback_boost(user_query)
```

## 7. 关键技术方案

### 7.1 SPA 数据获取策略

**问题**：若依 Vue.js SPA，页面 HTML 是空壳 (`<div id="app"></div>`)，所有数据通过 AJAX 动态加载。

**方案**：不渲染页面，直接调后端 API。

**实现步骤**：


### 7.2 LLM JSON 输出稳定性保障

**问题**：LLM 有时不严格输出 JSON（包裹 markdown 代码块、添加解释文字、JSON 格式错误）。

**方案**：多层容错 + 约束性 Prompt。

```
层面 1 — Prompt 约束:
  System: "你是一个数据提取助手。只返回合法的 JSON 对象，不要包含任何 markdown 标记或解释文字"
  temperature=0.1 (低温度提高确定性)

层面 2 — 输出清洗:
  1. 直接 json.loads(content)
  2. 失败 → 正则提取 ```json ... ```
  3. 失败 → 正则提取 { ... }
  4. 失败 → 返回错误摘要，触发重试

层面 3 — 重试机制:
  MAX_RETRIES = 2
  字段缺失时 → 构造修正 Prompt → 追加 "上次返回缺少字段 {xxx}" → 重试
```

### 7.3 字段映射自适应

**问题**：不同 API 返回的 JSON key 命名不统一（`nurseName` vs `doctor_name` vs `elderlyName`），用户用中文描述需求，系统需要做语义映射。

**方案**：LLM 驱动的字段映射。

```python
# 用户输入
fields = ["姓名", "工号", "科室"]

# API 返回原始数据

field_mapping = {
    "姓名": "nurseName",    # "姓名" ↔ "nurseName" (语义: nurse + name)
    "工号": "jobNumber",    # "工号" ↔ "jobNumber" (语义: job + number)
    "科室": "deptName",     # "科室" ↔ "deptName" (语义: department + name)
}
```
